# P1-03: детерминированное исполнение fast-evaluation задач

Следующий инкремент: [cold bootstrap/provenance](p1-offline-bootstrap.md). При использовании восстановленного engine окна обязаны продолжать hash/sequence цепочку без пропусков.

25 сентября 2026. `OfflineScheduledReplay` расширяет компонентный offline adapter на непрерывные окна с несколькими корневыми обработчиками и fast-evaluation задачами. Полный session dispatcher и восстановление начального состояния из manifest ещё не реализованы.

## Исполнение

Live engine получил два адаптера: `_launch_event_evaluation` создаёт обычную asyncio Task, `_event_evaluation_sleep` выполняет обычный sleep. Стратегия, тайминговые расчёты и арбитраж остались в прежнем `_run_event_evaluation`.

Offline adapter запускает эту же coroutine пошагово. Вместо Task используется сохранённый ContextVar context, вместо реального ожидания — контролируемая точка приостановки. Записи журнала определяют старт, resumed и completion; виртуальное время поступает только из строгого cursor. Состояния и задержки не вычисляются повторно другим алгоритмом: реальные вызовы обработчика должны совпасть с записанными.

Поддерживаются обработка рынка, пока задача ожидает; coalescing повторных сигналов; независимые задачи нескольких символов; отмена до первого запуска и во время ожидания; отложенная запись finished после завершения coroutine. Вложенные evaluate/arbiter scopes выполняются самим движком. Новые task IDs определяются исходной позицией в input journal.

Неподдерживаемое await, неверный task ID/parent scope, незавершённые задачи в конце окна, нарушение hash/sequence chain или несовпадение output events приводят к отказу. Начальное состояние до окна задаёт вызывающая сторона. Между окнами не допускается перенос незавершённых задач. `parityReady=false`.

## Найденный и исправленный дефект live

При отмене asyncio Task до первого запуска тело `_run_event_evaluation`, включая finally, не исполняется. Ранее оставался `event_eval_pending=true`, из-за чего следующие события могли coalesce с уже отменённой задачей, а fallback evaluation пропускалась.

Теперь session хранит owner текущей задачи, а done callback вызывает общий `_complete_event_evaluation`. Он очищает pending/capture ID/latency message только при совпадении owner. Поздний done callback старой задачи не очищает новую. Offline completion вызывает тот же метод. Исправление проверено при capture on/off: после отмены до старта следующий сигнал создаёт новую задачу.

## Проверка и границы

Полный набор: **629 passed**, 43.78 секунды в чистом окружении. Добавлены десять тестов scheduler и отмены задач.

Тесты сравнивают input/clock observations, output events, market snapshot и счётчики scheduler. Проверены два символа, рынок во время sleep, coalescing, обе отмены и ошибки с корректно пересчитанной hash chain. Во время replay asyncio.sleep/create_task заменены запретом. Fixture явно задаёт engaged state; это проверка порядка исполнения, а не доказательство прибыльного сигнала.

Adapter сохраняет и восстанавливает instance overrides и временные зависимости engine. При ошибке закрывает приостановленные coroutines в их контекстах и запрещает повторное использование экземпляра: торговое состояние не откатывается. Как и segment adapter, это компонентный API с подготовленным engine, не процессная сетевая песочница и не загрузчик полного JSONL.

Следующий шаг — восстановление config/policy и исходного состояния с проверкой provenance, затем clock/scanner/control/UI/periodic/transport dispatch. После этого нужны load validation и полная parity сделок/PnL. Новый длительный пользовательский прогон пока не требуется; текущий сервер этим изменением не перезапускался.
