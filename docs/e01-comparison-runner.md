# E01: сравнение двух paper-портфелей

Обновление: реализован [отдельный live collector для 30-минутного smoke](e01-smoke.md). Он пишет sealed e01-feed-v2 и полные события на диск, поддерживает общий REST context и записанные health callbacks. Ниже описано также исходное v1/offline ядро; ограничения memory recorder относятся к standalone compare-e01.py, не к live collector.

Проверки после разбора второго live smoke: **799 passed** за 117.20 секунды во всём наборе при SCALP_DISABLE_DOTENV=1; профильные market-context/E01/golden — 49 passed. `git diff --check` проходит. [Второй сетевой smoke](e01-smoke-02-results.md) не завершён из-за backpressure; оптимизированы расчёты flow и копирование, подготовлен smoke-03.

Реализованы экспериментальный veto в общем арбитре и модуль E01Comparison с файловым runner scripts/compare-e01.py. Рабочий запуск приложения не переведён на E01: e01_breakout_obstacle_veto по умолчанию false, существующие профили не менялись.

## Единственное различие вариантов

Baseline и candidate создаются из одинаковой публичной конфигурации. Baseline принудительно получает e01_breakout_obstacle_veto=false, candidate=true. Поле включено в config hash и run manifest. Секреты/окружение не используются для восстановления настроек сравнения.

Candidate добавляет blocker e01_foreign_obstacle_before_first_take, если исходный structural assessment показывает чужое препятствие до первой фиксации для level_breakout. Проверяется до планирования, после пересчёта плана и в финальном сравнении кандидатов. Исключение для собственного уровня использует существующую семантику generation; совпадение цены с day high/low само по себе не даёт исключения. Veto распространяется и на добавление новой экспозиции через breakout add. Управление уже открытой позицией не изменено.

У вариантов разные engine, strategies, sessions, broker, balances, pending entries, cooldown и recorder. Входные данные глубоко копируются. Разница в позициях может менять последующие размеры/допуски и состав активных инструментов — это часть портфельного эффекта, а не ошибка сравнения.

## Поддержанный источник

Runner принимает **специально подготовленный e01-feed-v1** и sealed **e01-feed-v2** от live collector, не старый session JSONL и не replay-input-v4. Автоматический конвертер этих журналов не реализован. V1: первая строка содержит schema и полный config по PUBLIC_CONFIG_FIELDS, последующие строки имеют ровно kind, symbol, body, wallSeconds, monoNs. V2 дополнительно связывает конфигурацию/source/runtime и observations цепочкой хешей с sequence и обязательным footer; source/runtime сверяются перед повтором.

Поддержаны:

- scanner: общий список candidates и карта bootstrap-результатов новых кандидатов из top working_symbols, которых может продвинуть хотя бы один портфель. Оба движка самостоятельно применяют исходные ranking/promotion/cleanup.
- clock_sample/clock_error: общий результат синхронизации.
- market_message: исходный MarketMessage body по контракту input_journal; источник должен покрывать объединение активных инструментов обоих вариантов.
- rest_context: общий результат обновления 1m/5m/15m/1h по контракту input_journal.
- health: общий вызов market_health с фиксацией изменений диагностического состояния часов.
- evaluate и arbiter: явно заданные вызовы по одному расписанию.
- start и stop: одинаковые операторские границы.

event_driven_evaluation_enabled должен быть false, research_policy_mode — off. Другие режимы явно отклоняются. Сеть и фоновые задачи не запускаются; общий feed управляет часами. По истечении paper_run_duration_seconds оба варианта останавливаются перед обработкой следующего наблюдения; для точной временной границы producer обязан прислать stop вовремя. При finish оставшиеся позиции закрываются по последнему состоянию рынка по одинаковому правилу comparison_end.

Поток должен передавать результат bootstrap даже для кандидатов, нужных только одному портфелю. Команды после окончания окна продолжают обновлять рынок, но повторный Start запрещён. При неподдержанном событии, нарушении monotonic clock или лимита наблюдений comparison становится failed и не выдаёт успешный финансовый отчёт.

## Запуск на подготовленном файле

Из корня репозитория:

```powershell
.\.venv\Scripts\python.exe scripts\compare-e01.py data\e01-feed.jsonl --output data\e01-result.json
```

Это формат команды, а не указание, что data/e01-feed.jsonl уже существует. Лимит по умолчанию 100 000 наблюдений, изменить можно через --max-events. Файл результата создаётся только новым. Runner читает вход построчно, но события/сделки портфелей сохраняются в памяти: длительная запись под нагрузкой пока не проверена.

Отчёт содержит manifests, общий последовательный input hash, eventsConsumed, сделки, fees, balance/net обоих вариантов и netDifference=candidate−baseline. Сделки берутся из полного журнала trade_closed, а не broker.closed_trades, усечённого до последних 200; число закрытий сверяется с total_closed_trades. Исходные events сохранены для проверки отказов и финансовой цепочки. Статус comparison_completed означает завершённую симуляцию; profitabilityProven и parityReady остаются false. Никакой синтетический результат не принимается за доказательство преимущества фильтра.

## Проверки и следующий шаг

Проверяются long/short, собственный/чужой уровень, неизменность других playbooks, pre/post/final admission, независимость объектов/капитала, исходная production breakout-стратегия на общем синтетическом feed, сериализация отчёта и отказ на неподдержанном вводе/превышении лимита. Отдельный controlled-candidate test подтверждает baseline open против candidate veto без ручного создания позиций; он не доказывает качество production-сигнала.

Следующий шаг — выполнить 30-минутный smoke и проверить запись/нагрузку. Затем завершить подсчёт уникальных кандидатов и различающихся допусков, equity/drawdown и суточные метрики по [дизайну E01](e01-breakout-obstacle.md). Только после этих проверок выдавать команду длительного прогона. Текущий live collector ограничен техническим smoke, 72-часовой запуск ещё не готов.
