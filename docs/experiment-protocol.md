# Протокол сравнительного исследования

Цель — получить проверяемое решение по одной гипотезе. Отрицательный результат и недостаточность данных являются полноценными исходами.

## Карточка до запуска

Заполнить и сохранить в репозитории до изучения результатов:

- ID, вопрос, причинный механизм и ровно одно проверяемое изменение.
- Baseline и candidate: commit/dirty diff, manifest hash, стратегии, universe и правила scanner.
- Источник данных, временные блоки настройки и нетронутой проверки; исключённые интервалы и причины.
- Общие правила исполнения, latency/cost assumptions, размер/денежный риск, initial capital.
- Единица наблюдения: уникальное рыночное событие/кандидат; правила дедупликации и зависимых сделок.
- Основная метрика, допустимые риски, минимально полезный эффект, метод оценки неопределённости и заранее заданное правило окончания.
- Правила остановки из-за качества данных; запланированные дополнительные срезы; журнал уже проверенных вариантов.

Не использовать future extrema как исполнимые вход/выход. Не выбирать удобный конец эксперимента после появления положительного PnL. Не считать переименование профиля новой независимой стратегией.

## Во время запуска

Один поток данных, две независимые paper-модели baseline/candidate с одинаковым бюджетом и исполнением. Портфели не должны делить лимиты или изменять друг другу очереди. Смена настройки/стратегии фиксируется и завершает сопоставимый сегмент. Изменённый сегмент не смешивается с неизменным.

Вести цепочку: market event → candidate → admission/rejection → order intent → executable arrival/fill/cancel → partial/exit → net outcome. Сохранять отказы, а не только исполненные сделки. Частота decision updates не равна количеству сетапов.

## После запуска

1. Проверить session integrity; при нарушениях сначала разобрать данные. В v1 используется `scripts/validate-session.py`; непроверяемые им свойства перечислены в отчёте.
2. Проверить соответствие manifest и replay parity. Эти проверки ещё реализуются по roadmap.
3. Посчитать net на весь lifecycle, gross, fees/funding, fill rate, expectancy, drawdown, хвостовые потери, MAE/MFE и time-to-response. Учитывать уже встроенное в fill проскальзывание без повторного вычета.
4. Показать все исходы: спасённые потери, потерянные выигрыши, новые сделки и изменённые размеры/лимиты.
5. Отдельно оценить зависимость от дня, инструмента и общего рыночного события. Использовать временные блоки для holdout/оценки неопределённости; не считать коррелированные сделки независимыми.
6. Проверить устойчивость к реалистичному ухудшению execution assumptions.
7. Принять один вывод: принять кандидата в следующий этап / отклонить / недостаточно данных. Зафиксировать evidence artifact и следующий эксперимент.

## Краткий формат результата

| Поле | Содержание |
|---|---|
| Experiment/manifest | Проверяемая неизменная версия |
| Data quality/parity | Passed, failed или unknown, причины |
| Unique events / trades | Baseline/candidate и покрытие |
| Net effect | В деньгах и нормированном риске, после всех расходов |
| Uncertainty/concentration | Временные блоки, инструменты, зависимость от выбросов |
| Tradeoffs | Удалённые выигрыши, новые убытки, fill/turnover |
| Decision | Accept next stage / reject / insufficient data |

Встроенные hindsight opportunity labels помогают находить эпизоды для изучения. Они не являются ground truth о доступных прибыльных входах и не заменяют этот протокол.
