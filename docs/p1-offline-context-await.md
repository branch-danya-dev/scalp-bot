# P1-03: события во время ожидания REST-контекста

Следующий инкремент: [scanner/bootstrap REST-await](p1-offline-source-await.md).

Добавлена запись и воспроизведение ожидания пакетного обновления свечей. Рыночные обработчики, UI и другие поддержанные задачи теперь могут выполняться между началом загрузки и применением результатов. Это ограниченный шаг к полной session parity, не её подтверждение.

## Контракт записи

Экспериментальный `replay-input-v4` расширен событием `context_await`:

- `wait`: уникальный возрастающий ID batch и упорядоченный список symbols, до запуска refresh coroutines;
- `request`: ID batch и symbol, непосредственно перед проверкой свежести 1m в соответствующей refresh coroutine;
- `ready`: ID batch после завершения внешнего gather, до применения результатов;
- `cancelled`: ID batch при отмене ожидания gather. Неполный batch не применяется.

Проверка свежести остаётся на исходном месте и использует реальные clock reads. Порядок запуска корутин, вложенные gather и REST-запросы live-кода не меняются. Параллельные ответы применяются в прежнем порядке instruments, частичные ошибки остаются SourceFailure в offline-адаптере.

`request` означает начало обновления инструмента, а не отправку отдельного HTTP-запроса. `ready` — завершение ожидания всего batch, а не точное время каждого HTTP-ответа. Внутренние запросы интервалов не меняют торговое состояние до применения batch; их сетевой порядок и retry здесь не воспроизводятся.

Новый вид события — добавочное расширение экспериментальной v4. Старый reader его отклонит. Новый reader читает прежние записи без этих границ, но не восстанавливает отсутствующий порядок ожиданий. Cold restore по-прежнему требует совпадения source/runtime fingerprints; обновление reader не разрешает запуск старой записи против изменённого движка.

## Offline-поведение

Context loop приостанавливается на детерминированной границе. Dispatcher продолжает исполнять другие записанные обработчики. На `request` возобновляется проверка свежести нужного инструмента; на `ready` восстанавливаются результаты и общий loop применяет их. На `cancelled` корутина получает CancelledError, не применяя результаты.

Нет сетевых запросов, asyncio Tasks, реального sleep или ускоренного времени. Неверные ID, symbol, преждевременный ready, потерянное завершение и незавершённое окно приводят к отказу. Валидатор отдельно проверяет lifecycle batch и незавершённые ожидания перед footer.

## Проверка и оставшаяся работа

Полный набор: **708 passed** за 83.76 секунды в чистом окружении; 16 новых тестов. `git diff --check` проходит.

Fixture воспроизводит bootstrap → context wait/request → snapshot стакана → public_state → ready/apply либо cancellation. Сравниваются исходные output events, свечи, стакан и engine events. Проверки включают перехешированные семантические повреждения и структурный валидатор.

Пока поддержано ожидание context batch. Scanner, bootstrap и clock REST-await interleaving, global context errors, другие неподдержанные ошибки и потоковый replay остаются открытыми. Ожидания не переносятся между replay-окнами. Далее — границы ожидания scanner/bootstrap и их диагностика, затем capture load validation и сравнение полной торговой сессии.

Правила входа/выхода и профиль запуска не менялись. Новый длительный прогон пока не требуется; сервер не перезапускался.
