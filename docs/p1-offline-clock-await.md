# P1-03: ожидание синхронизации часов

Следующий инкремент: [диагностика scanner/bootstrap failures](p1-offline-source-diagnostics.md).

Проверка: **733 passed** за 90.87 секунды в чистом окружении, 11 новых тестов. `git diff --check` проходит.

`source_await` в экспериментальной v4 поддерживает `source=clock`, symbol=null. Live записывает wait перед clock_sample и ready после получения результата, до изменения MarketClock. Отмена записывается как cancelled и не меняет последнюю синхронизацию.

Ошибка REST представляется SourceFailure с исходным типом, после ready записывается clock_error общим обработчиком. Здесь ready означает доставку результата операции, включая ошибку, а не успешную синхронизацию. Текст исключения не записывается. Offline не создаёт исключений из строк; он вызывает общий обработчик clock_sample либо clock_error после записанной границы ожидания.

Scheduled replay поддерживает отдельный clock_sync, periodic clock loop и sync внутри service start. Пока ответ ожидается, другие поддержанные обработчики могут изменять состояние. Segment adapter по-прежнему принимает только соседние wait/ready без interleaving.

Проверено истечение срока прежней синхронизации во время запроса, с промежуточным snapshot стакана, public_state и arbiter. После успешного ответа синхронизация восстанавливается; ошибка, отмена и ответ с чрезмерным RTT не делают устаревшую синхронизацию пригодной. Восстановление часов само по себе не подтверждает свежесть остальных рыночных данных.

11 новых тестов сравнивают output events, MarketClock, clock_reading/block_reason, стакан и engine events для отдельного и периодического вызовов. Перехешированные неверные source/ID и отсутствующий результат отклоняются. Offline не вызывает сеть, Tasks/gather/sleep. Структурный validator проверяет полную запись до footer.

Остаются scanner/bootstrap/global-context error outputs, прочие неподдержанные исключения, rejected controls, потоковый replay и capture load validation. Ошибка применения clock_sample после его записи также не считается поддержанной REST-ошибкой. Полная торговая session parity и готовность к prod не заявляются.

Следующий шаг — воспроизводимая диагностика остальных ошибок источников, затем streaming/load validation и сравнение полной торговой сессии. Правила торговли и профиль не менялись; сервер не перезапускался, новый длительный прогон пока не нужен.
