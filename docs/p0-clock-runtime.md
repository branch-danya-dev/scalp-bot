# P0-04: подключение биржевого времени

Реализовано 25 сентября 2026. Это техническое исправление временной базы, не изменение критериев breakout/rejection и не подтверждение доходности.

## Что изменилось

- `BybitRestClient.clock_sample()` получает `timeNano` через публичный [GET /v5/market/time](https://bybit-exchange.github.io/docs/v5/market/time). RTT измеряется от отправки успешной HTTP-попытки до получения её ответа. Ожидание pacing и предыдущие неуспешные попытки не относятся к этому server timestamp и исключены из интервала. Грубый fallback на `timeSecond` не используется.
- При старте сервиса выполняется синхронизация, далее — раз в 20 секунд после принятого ответа. После отказа или ошибки повтор — через 2 секунды (либо меньший настроенный интервал); HTTP retries/pacing дополнительно влияют на фактическое время. Холодный старт без пригодных часов также использует короткий интервал. MarketClock строит границы биржевого времени и продвигает их через perf_counter. Последний принт не используется для коррекции часов.
- Перекрывающийся новый диапазон может сузиться ниже последнего evaluation timestamp. В этом случае верхняя граница консервативно расширяется до предыдущего evaluation, только если старый anchor ещё не просрочен и итоговая uncertainty укладывается в прежний лимит. Величина записывается как `upperPaddingMs`. Непересекающийся откат блокируется; TTL и лимиты не повышены.
- Медленный или слишком неопределённый новый образец отклоняется, но не сбрасывает ранее принятый. Старый образец действует только до исходного срока истечения/предела uncertainty; отказ обновления не продлевает его жизнь и не снимает fault скачка часов. Без пригодного образца входы запрещены. Причина отображается в market health отдельно от WebSocket readiness.
- Feature/strategy evaluation, forming candle, flow/OFI и управление инвалидацией получают согласованный timestamp. Исходные timestamps рынка сохраняются. Внутри public-trade batch исполнение видит только уже обработанный префикс.
- Возраст fast/deep book и tape берётся из исходного `receipt_mono_ns`, а не времени извлечения сообщения из очереди. Отдельно проверяется возраст самого биржевого события относительно clock bounds. Обновление одной ленты не освежает остальные.
- Недостоверные часы запрещают новые входы и staged adds, снимают pending entries и очищают старые решения. Hard stop/target для открытых позиций продолжают исполняться. Стратегическая инвалидация при invalid clock не использует недостоверный контекст.
- В новом режиме таймауты pending entries, no-follow-through, grace period и длительность прогона используют монотонное время. Wall timestamps остаются для отображения/журнала. Funding использует время открытия в биржевой шкале и пропускает расчёт при отсутствии достоверного exchange observation.
- Записываются `clock_sync`, `clock_sync_error`, `clock_admission_changed`, clock readings и receipt ages в frames. Это позволяет различить слабый сигнал и отказ из-за качества данных.

`SCALP_EXCHANGE_CLOCK_ENABLED=true` включён в `.env.example`, который загружается стандартным launcher. Bare `Settings()` оставляет legacy-режим для существующих детерминированных тестов/replay; запуск напрямую без checked-in профиля требует явного включения. Оба режима фиксируются в manifest v3. Сравнивать старый baseline и новую конфигурацию как неизменный эксперимент нельзя.

## Проверки и ограничения

Полный набор тестов проверяется в чистом окружении. Новые engine-регрессии: принт впереди local wall, независимое устаревание fast/deep/tape, задержанный batch, недоступная/просроченная синхронизация, отмена pending до fill, работа hard stop при invalid clock и устойчивость таймаутов к wall jump. Старые 539 тестов остаются в наборе.

Read-only probe публичного endpoint с этого компьютера: RTT 594.8 мс отклонён; 244.6 и 256.4 мс приняты. В принятых ответах server timestamp был на 228.1/227.7 мс впереди local receipt wall. Это не точная оценка clock offset — в ней есть задержка доставки. Торговый сервер и сделки этим probe не запускались. Локальные данные: `data/audit-20260925/clock-probe.json`.

Получены первый [15m smoke и исправления](p0-clock-smoke-results-2026-09-25.md) и [повторный smoke v2](p0-clock-v2-results-2026-09-25.md). Во втором ложных rollback нет, upper padding реально применяется; одна просрочка синхронизации примерно на 1.36 секунды сопровождалась блокировкой и восстановлением допуска. Строгий integrity validator сохраняет rejected по пяти invalid-clock frames. Продолжительный reconnect/fault stress и полный replay parity остаются открытыми задачами. Повторять одинаковый smoke без новой гипотезы сейчас не требуется.

Валидатор v3 для `exchange-bounds-v1` считает разницу exchange timestamp / local record диагностикой, а не доказательством нарушения causality. Он по-прежнему отклоняет invalid clock, некорректные bounds, принт после exchange upper bound или времени контекста. Старые записи без этого контракта проверяются по прежним правилам. Проверка арифметики bounds не доказывает независимую точность серверных часов или достоверность подменённого журнала.

## Технический paper smoke — 15 минут

Сначала штатно остановить старый сервер. В PowerShell:

```powershell
cd G:\scalp-bot
.\scripts\run.ps1 -Profile .env.research-p0-clock-smoke-15m
```

После preflight открыть `http://127.0.0.1:8000/`, дождаться синхронизации/свежих потоков и нажать Start. Первый холодный запрос может превысить RTT threshold; следующая синхронизация выполняется автоматически. Не увеличивать допуски ради запуска без разбора причин.

Через 900 секунд торговля остановится; Ctrl+C завершает сервер и запись. Не переключать стратегии. Проверить новый файл через `scripts/validate-session.py`, сохранив отчёт по новому пути. Количество/прибыльность сделок не является критерием этого smoke. Критерии: полный Start/Summary с manifest, отсутствие необъяснённых временных противоречий и потерь записи, диагностируемые clock/admission transitions. После этого — решение о более длительной записи и переходе к P1/E01.
