# Архитектура первой модели

## Решение и границы M0

В одном проекте остаётся один scanner, рыночное состояние, риск и исполнитель.
Параллельно существуют обычные playbooks и `trend_impulse_ml`.
M0 реализует только неизменяемые сообщения и чистую таблицу выбора. Всё ниже,
кроме этих контрактов, — план M1–M5, не уже работающая интеграция.

## Поток

Общие упорядоченные рыночные события → существующие признаки →
(a) обычные стратегии без ожидания ML; (b) неизменяемый snapshot → локальный worker →
ImpulseForecast → ImpulsePlanPolicyV1 → торговое предложение → общий dispatcher →
RiskEngine/атомарный резерв → PaperBroker → сопровождение владельцем.

Предиктор не имеет биржевого клиента, учётных ключей, права менять счёт, stop/risk
и чужие позиции. Первая модель оценивает исходы продолжения; детерминированная
ML-стратегия задаёт причинную область входа, отмену, target/stop и timeout. ML не
должна подтверждать зрелый breakout-уровень, если её сетап — независимый импульс.
Сопровождение v1 фиксировано; learned exits, sizing и обмен трендом отложены.
Профиль исполнения для нового ключа нужно объявить явно, без fallback по неизвестному
имени. Существующие доли partial и режимы других владельцев не меняются.

## Правила выбора

`ml/arbitration.py` — исполняемая спецификация будущего dispatcher, не его замена.
`ml_ready` означает свежий полный план с предварительной экономикой, не raw score.

| Состояние | Выбор |
|---|---|
| FREE / OBSERVING / PREPARING | Готовый rule побеждает; иначе готовый ML может завершить наблюдение и получить новый сценарий |
| READY обычного сценария | Rule имеет приоритет; противоречивое READY без плана не отдаёт монету ML |
| RESERVING / ORDER_PENDING / PARTIAL_FILL / IN_POSITION | Перехват запрещён |
| CANCELLING / RECONCILING | Монета занята до подтверждённого результата; late fill принадлежит исходному владельцу |

Выбор+финальная проверка состояния+резерв выполняются атомарно в одном executor.
Между двумя монетами также общий риск; модели не выдаётся второй независимый депозит.
Нет ожидания медленного predictor и нет задержки для сбора «всех голосов».
После выбора владелец заявки/позиции неизменен. Переключение ожидания на ML —
явный transition с причиной; обратно тот же импульс не переименовывается.
Отказ экономики одной стратегии нельзя обойти новым именем источника на том же
эпизоде. Нет автоматического ML-veto или безусловного приоритета ML.

## Время и сообщения

SnapshotRef: capture/symbol, selection_epoch, source_sequence, market_time_ms,
available_mono_ns, clock_domain, feature_schema. Market time и монотонные длительности
не вычитаются друг из друга. Domain включает запуск/источник логических часов;
разные машины/перезапуски не сравниваются без явного преобразования.

FeatureSnapshot хранит упорядоченные имена и tuple чисел/None. None означает
отсутствие, не нулевой поток. Порядок, единицы и missing policy фиксируются хешем
схемы. Производитель гарантирует доступность всех признаков на source_sequence;
валидация dataclass сама этого доказать не может.

ImpulseForecast: ссылка на snapshot, версия модели/plan policy, сторона,
горизонт, produced/expires и вероятности target-first / stop-first / timeout.
Это вероятности исходов **одной стороны одного фиксированного плана**, не сумма
независимых long/short прогнозов. Позднее завершение predict не освежает исходные данные.
`forecast_rejections()` проверяет метаданные/возраст; отсутствие причин отказа
не даёт права на ордер. Цена, глубина, здоровье данных и риск проверяются исполнителем.

## Производительность и отказоустойчивость

Один локальный worker; ограниченное число потоков (стартовый кандидат thread_count=1),
без обещания конкретных миллисекунд до замера. Windows spawn/import-safe entrypoint.
Отдельный процесс всё равно делит CPU/RAM; обучение вне торгового процесса/нагрузки.

Bounded latest-snapshot mailbox на символ. Можно объединять задания на прогноз,
но нельзя выбрасывать raw orderbook deltas до восстановления общего состояния.
При недостаточном окне данных ML воздерживается. Queue lag, stale/coalesced/dropped,
predict p50/p95/p99, data→proposal, RSS/CPU и main-loop p99 измеряются отдельно.
Численные latency budgets/TTL и лимиты ресурсов фиксируются до нагрузочного теста,
исходя из горизонта/машины; M0 не выдаёт непроверенный budget за достигнутый SLA.

Shadow пишет версии входа/выхода и причины отказов отдельно от торговых outputs.
Ошибки worker останавливают новые ML-входы; основной бот и защита ML-позиций живут
без worker. Обновление весов только между сессиями, доверенный artifact+SHA;
никакого автоматического pickle из неизвестного источника или online дообучения.

## Прогнозный контекст — позже

Модельный trend не подменяет market facts. Экспорт в обычные стратегии — отдельный
эксперимент после самостоятельного теста модели. Он не меняет наблюдённые уровни
и не разрешает двигать цель ради R:R. Вероятности требуют проверки калибровки.
