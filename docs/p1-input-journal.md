# P1-02: контракт и экспериментальный захват входных событий

**Текущая версия — v4:** [периодические вызовы, UI, transport и policy](p1-input-journal-v4.md), ранее — [чтения часов и границы вычислений](p1-input-journal-v3.md) и [bootstrap/REST/scanner/lifecycle](p1-input-journal-v2.md). Ниже сохранено описание первого инкремента v1. Validator понимает v1–v4 и всё ещё не разрешает parity.

Реализовано 25 сентября 2026. Версия `replay-input-v1`. Это первый захват входов в существующем runtime, **не полный журнал, пригодный для parity**. Отсутствующее покрытие явно записано в header и возвращается валидатором. P1-02 остаётся в работе.

## Реализованная запись

`TradingEngine(config, clock=..., capture_inputs=True)` включает экспериментальный захват в SessionRecorder. По умолчанию он выключен; текущий launcher и paper-профили его не включают. Не добавлен новый скрытый параметр Settings: опция capture и её неполное покрытие объявлены в отдельном header. Это программный API для интеграционных проверок, пока не рекомендация следующего пользовательского прогона.

В JSONL добавляются события `replay_input`, содержащие:

- `schema`, общий для экземпляра engine `sequence`, `previousHash`, `hash`;
- `kind`, `symbol`, `body`;
- `processingWallSeconds`, `processingMonoNs` — наблюдение при записи до соответствующего обработчика.

Номер обозначает порядок записанных границ обработки, а не биржевой порядок и не полный порядок завершения асинхронных задач. Внутри сообщения порядок исходного batch сохраняется. Пакеты не сортируются по exchange timestamp. Исходные receipt timestamps сохраняются отдельно; отсутствующее время получения остаётся нулевым и учитывается валидатором, а не заменяется временем обработки.

| Kind | Точка захвата |
|---|---|
| `header` | Создание engine с включённым capture; schema и фактическое неполное покрытие |
| `market_message` | Вход в on_message после разрешения symbol, до изменения его состояния |
| `clock_sample` | Полученный REST time sample перед MarketClock.synchronize |
| `clock_error` | Тип ошибки синхронизации без текста ответа/секретов |
| `callback` | Вход в `_evaluate` или `_arbitrate_once` |
| `control` | Запрос Start/Stop, вызов остановки по таймеру, переключение стратегии |
| `footer` | После отмены и ожидания фоновых задач, перед закрытием recorder |

Control фиксирует запрос, включая отклонённый/no-op; сам факт записи не означает, что команда успешно выполнена. Body содержит только определённые схемой поля. Рыночный body — allowlist topic/type/ts/cts/data, receipt/processing telemetry и event ID. OTel span, транспорт, credentials и headers не сериализуются. Содержимое публичного data сохраняется полностью, без усечения глубины или batch.

До передачи recorder выполняется JSON-копирование и вычисление SHA-256. Поэтому последующее изменение исходного объекта не изменяет уже поставленную в очередь запись. В header не записываются `.env` или секреты. Цепочка хешей обнаруживает несогласованные изменения, но не удостоверяет автора: целенаправленно переписанный и заново хешированный журнал не становится криптографически аутентифицированным.

## Потери и завершение

Журнал использует существующую ограниченную очередь. Его строки относятся к bulk telemetry, чтобы не вытеснять критичные trade events. Счётчик sequence продвигается даже при потере строки recorder: промежуточные потери обнаруживаются по последовательности/цепочке, потеря хвоста — по отсутствию footer. Footer включает число входов; наличие целого footer не компенсирует пропуски до него. Остановка торговли по таймеру не закрывает capture: footer возникает при штатном закрытии engine.

Большие полные book updates, JSON-копирование и хеширование создают дополнительные CPU/I/O затраты. Их влияние на latency и drops под реальной нагрузкой ещё не измерено. Включать захват по умолчанию до завершения покрытия и нагрузочной проверки нельзя.

## Валидатор

```powershell
.\.venv\Scripts\python.exe scripts/validate-input-journal.py data/sessions/session-20260925T091451Z.jsonl --output data/audit-20260925/new-input-report.json
```

Проверяется фиксированный byte snapshot открытого файла, читаемый построчно с ограничением размера строки 16 MiB. Отчёт содержит SHA-256 snapshot, счётчики и коды ошибок; raw payload/config в него не копируются. Существующий output не перезаписывается.

`structuralStatus`:

- `checks_passed`: структура текущего частичного формата цела, есть header/footer, последовательность, hashes и processing order согласованы;
- `incomplete`: захват отсутствует либо нет штатного завершения;
- `rejected`: пропуск/перестановка/дубликат, неверный hash/schema/body, clock reorder, receipt позже processing, неверный footer, повреждённый/слишком большой JSONL row.

`parityReady` **всегда false для этой версии**. CLI возвращает 1 при структурном reject, иначе 2, а не код успешной parity-проверки. `structuralStatus=checks_passed` нельзя использовать как разрешение сравнивать PnL. Поля coverage не принимаются на веру: header с заявлением полного покрытия не соответствует этой схеме.

Проверка последнего реального smoke: [coverage report](validation/p1-input-coverage-smoke-v2-2026-09-25.json), `incomplete`, `coverage=not_recorded`. Это ожидаемо: старый процесс не записывал replay_input. Его research frames не повышаются до полного входного потока задним числом.

## Что требуется до полноценного replay

В header явно перечислены отсутствующие группы:

1. Полный bootstrap и REST context: свечи всех горизонтов, instrument/fee/funding metadata, результаты обновлений и ошибок.
2. Scanner, symbol activation/deactivation и начальные состояния book sequencer/reconnect.
3. Каждое значимое чтение runtime clock внутри обработчика, включая watermark MarketClock: одного наблюдения на callback недостаточно.
4. Dispatch/completion/coalescing асинхронных вычислений и причинная связь вложенных вызовов.
5. Привязка начального состояния и входного потока к проверенному manifest/config/code и отдельным Start/Summary.

Следующий инкремент — закрыть эти группы через общий event adapter, после чего добавить offline dispatch и сопоставление выходов. Текущие hooks не должны заставлять offline driver повторно запускать вложенный callback, который уже вызывает обработчик сообщения. Нужен явно описанный порядок, а не перебор всех строк как независимых команд.

## Проверки

578 тестов проходят в чистом окружении. Новые регрессии: immutable copy, исходный receipt, отсутствие OTel объектов, hash/sequence gaps, перестановки/дубликаты, потеря footer, wall rollback при monotonic порядке, receipt из будущего, недопустимая схема, ограничение размера строки, невозможность объявить parity через подмену header. Интеграционный тест подаёт рыночное сообщение в настоящий symbol worker без сети и проверяет порядок clock sample → market message → callback. Capture по умолчанию не создаёт дополнительных записей.
