# Контракт времени и качества данных — P0

Статус: session-integrity v3 и интеграция MarketClock в engine/Bybit реализованы. Новая база включена стандартным launcher; [технический smoke](p0-clock-runtime.md) ещё требуется. Описание ниже сохраняет устройство компонента и границы гарантий.

## Различать три времени

- Exchange event time: время исполнения принта / события matching engine; используется в рыночных окнах только в согласованной шкале.
- Local receipt time: момент фактического получения; определяет доступность события для стратегии.
- Monotonic time: интервалы внутри процесса, очередь и latency; не меняется при коррекции системных часов.

Replay использует виртуальные часы и порядок доступности событий. Нельзя раскрывать поздние принты из одного batch более раннему решению. Нельзя исправлять skew удалением верхней границы trade.ts <= observed_at или слепой заменой now на максимальный timestamp: так можно замаскировать stale и создать look-ahead.

Контракт реализации P0-04: оценивать и записывать clock offset/uncertainty; хранить исходные timestamp; задавать единый evaluation timestamp для согласованных признаков; независимо проверять возраст источников по receipt/monotonic. При скачке часов или недостаточной достоверности запрещать новые входы по явно определённому правилу, сохраняя управление существующими позициями.

## Валидатор записанной сессии v3

```powershell
.\.venv\Scripts\python.exe scripts/validate-session.py data/sessions/session-YYYYMMDDTHHMMSSZ.jsonl --output data/session-validation.json
```

Читает фиксированное число байт, определённое при открытии файла. SHA-256 относится к этому прочитанному префиксу. Дописываемый после начала проверки хвост не попадает в отчёт. Это не замена завершённому immutable raw archive. Input и существующий output не перезаписываются.

Память ограничена размером одной строки JSONL и компактными сводками по прогонам. Торговые границы определяются порядком `bot_started` → `run_summary`, а не всем временем жизни сервера. Market frames вне этих границ не загрязняют результаты. Несколько Start/Stop в одном файле разделяются; summary-счётчики broker трактуются как process-cumulative.

Проверяется:

- синтаксис JSON/envelope и полнота границ прогона;
- возврат локального времени назад по порядку записи;
- `formingCandle.lastTradeTsMs` позже local record/context observation;
- явные `tradeDeltaGap`, ошибки стратегии и переключение стратегий;
- recorder droppedRows/writerError, наличие recorder health;
- `gross − fees + funding = net` по закрытию и сверка run summary;
- наличие временных наблюдений; отсутствие evidence не превращается в успех.
- manifest/config/source/runtime hashes, принадлежность Summary и strategy toggle исходному manifest, повторное использование manifest ID между прогонами.

Manifest v2/v3 содержит версии Python и установленных distributions (только имена/версии, без installation paths и URL). V3 добавляет настройки новой временной базы; legacy-схема v1/v2 сохранена. Конфигурационные поля явно перечислены в `manifest_schema.py`; новая конфигурация требует пересмотра списка. Secret-поля не допускаются в публичный config. Валидатор не импортирует Settings и не читает локальный `.env`.

У старой сессии без manifest `provenance.status=unknown`: старые проверки могут пройти, происхождение кода от этого не становится известным. У manifest v1 без runtime fingerprint статус incomplete. `recorded_hashes_checked` подтверждает согласованность записанных hash, а не подлинность источника или равенство загруженного кода файлам на диске. Проверка ссылки Summary отражается отдельно в `summaryLink`. Hash не является цифровой подписью.

`--future-tolerance-ms` имеет default 0 и сохраняется в policy отчёта. Это допуск диагностики, не компенсация часов. Изменение допуска не исправляет runtime и должно быть обосновано до сравнения. Положительный возраст не доказывает синхронизацию: устаревший принт тоже может иметь положительный возраст.

| Status / exit code | Значение |
|---|---|
| checks_passed / 0 | Только реализованные проверки пройдены |
| rejected / 1 | Нарушения clock/data/accounting или изменение контролируемого профиля |
| incomplete / 2 | Недостаточно evidence, нет завершённого прогона/health/clock samples |

Повреждённый хвост/ошибка envelope отражается на статусе файла даже вне торгового окна: валидатор не маскирует нечитаемый источник. Ручная остановка отмечается warning; длительность сама по себе не доказывает пригодность исследования.

Не проверяются: полнота всех network events, подлинность/полная воспроизводимость окружения и загруженного кода, точное соответствие replay/live, корректность всех fills и прибыльность. Они явно перечислены в `notValidated`; `productionReady` всегда false. Отчёт агрегирует проблемы и хранит не больше трёх координат примеров на тип проблемы в прогоне; большие raw frames, конфигурационные значения и секреты в него не копируются.

## MarketClock: устройство компонента

`market_clock.py` принимает образец server time, полученный внутри явно заданного request/response интервала по монотонным часам. Он не делает сетевые запросы и не выводит поправку из цены или последнего trade timestamp.

На момент ответа границы exchange time: server timestamp минус precision и server timestamp плюс RTT плюс precision. Далее границы продвигаются монотонным временем и расширяются на заданный drift budget. Верхняя граница даёт evaluation time только для уже полученных и обработанных событий. Непрочитанные элементы WS batch нельзя включать в признаки даже при timestamp ниже этой границы.

Нет достоверного evaluation timestamp при отсутствии/истечении синхронизации, чрезмерном RTT/uncertainty, скачке локальных часов, rollback или обработанном событии за верхней границей. Будущий timestamp не подтягивает clock вперёд. Отдельная функция receipt age использует только monotonic и возвращает unknown при отрицательном возрасте.

Параметры компонента пока являются инженерными начальными ограничениями, не результатом сетевой калибровки: RTT ≤400 мс, возраст синхронизации ≤60 с, uncertainty ≤250 мс, wall jump threshold 250 мс, drift 50 ppm, timestamp precision 1 мс. Для реального адаптера точность server timestamp должна быть подтверждена; задержки/retries должны входить в измеренный интервал.

Адаптер, sample/reading telemetry, timestamp feature/strategy path и независимые receipt/event freshness для fast/deep/tape подключены. Invalid clock запрещает входы с продолжением защиты позиций. Engine-регрессии batch/stale и защитного исполнения реализованы; реальная запись и продолжительный reconnect/fault stress ещё нужны. Unit tests не подтверждают полноту live/replay parity.

## Регрессионные сценарии

Известный положительный локальный/биржевой skew; clock rollback; received-event causality внутри batch; задержка/перестановка; stale book/trades независимо; reconnect/gap; несколько прогонов в файле; расходы с funding; повреждённый JSON и отсутствие данных; дописывание файла во время анализа.

Тесты валидатора покрывают обнаружение нарушений в записи. Unit tests MarketClock покрывают skew, скачки и постепенный drift local wall, rollback, устаревание sync, большой RTT, рост uncertainty и событие вне границ. Engine-тесты покрывают received-prefix batch, независимый stale, признаки при offset и защитные выходы. Проверка реального длительного потока и reconnect/fault stress остаются в P0-04/P0-05.
